\begin{abstract}
We designed and implemented an IoT-based environmental monitoring device (EMD) that uses an ESP8266 microcontroller and a CD4051 analog multiplexer to provide multiple analog sensors to the single ADC of the ESP8266. It contains multiple sensors including DHT22 (temperature/humidity), MQ-6 (gases), LDR (light level), and soil moisture sensor. It displays readings locally on a JHD162A LCD (I2C) and transmits data via Wi-Fi to a Flask backend. The data is saved in SQLite or Supabase (PostgreSQL) and visualized using a React web application with Plotly charts. The use of an ML pipeline allows for the creation of LSTM models for multi-step predictions of the five environmental parameters based on recorded historical data, along with the use of an Isolation Forest model for detecting anomalies in the data recorded from all connected sensors. The models were trained on data recorded in a laboratory and deployed for five days; these results show that the system is stable and consistently operates with Wi-Fi connectivity, uploading the recorded data to a cloud service (supabase.com) every 10 seconds while maintaining data integrity through the use of an effective anomaly detection algorithm and accurate time-series predictions of sensor data.
\end{abstract}

\section{Introduction}
In the last few years, the importance of environmental monitoring has increased significantly as regards the smart building sector, the precision agriculture industry, industrial safety and laboratory quality assurance. The increased use of low-cost microcontrollers and their ability to connect to networks has made it possible to create devices that can use these microcontrollers to form distributed sensor networks capable of measuring temperature, humidity, air quality, light, and soil conditions in real-time, as well as transmitting that data to cloud or edge analytics platforms. The research in this area covers the integration of hardware, the development of communication protocols, the storage of data, the creation of data visualizations, and how ML can be applied for detection of anomalies and predictive analytics \cite{sensorcloud2019,mlanomaly2022}.

One of the most significant challenges with low-cost IoT nodes \cite{iotgas2023,esp8266data2022} is the lack of ADC resources. Many of the commonly used microcontrollers feature only one or a few ADC channels, and as a result, have a limited number of analog sensors that will be able to connect without using either an external expansion method or having to use multiple devices. Historically, analog multiplexers (MX) have been used in embedded systems to allow multiple analog sources to share the same ADC. However care must be taken with the design of the interface to account for channel selection timing, settling time, and wiring design to ensure that there is no crosstalk and that there are accurate measurements being taken.

The ongoing research of integrating various environmental parameters into a unified pipeline spanning from the acquisition of data through its eventual storage/visualization and the use of ML algorithms to make predictions and detect anomalies continues to be an area of focus in research initiatives, particularly when models are trained and tested exclusively using field/laboratory data rather than with synthetic data sets \cite{labmonitoring2020}. In this paper we discuss the design and evaluation of such a system along three axes: the use of a CD4051 multiplexer with an ESP8266 node to gather readings from gas, light, and soil moisture sensors via one ADC plus digital temperature and humidity sensors; the implementation of a back end and web-based dashboard to store and visualize the collected data; and the provision of an ML pipeline with LSTM-based time-series predictions and Isolation Forest--based anomaly detection, trained using only data collected during five days of deployment in the laboratory. This study is intended as a research-oriented treatment of the hardware, software, and ML integration rather than simply being a project report; the focus is on documented and reproducible design decisions, data handling, and evaluation methodologies. The key contributions are a documented interface for connecting a CD4051 to an ESP8266; methods for designing and building an environmental monitoring system; a substantial corpus of temporal environmental data (to our knowledge not currently available elsewhere in the same form); and a structured ML pipeline with multiple algorithms for prediction and anomaly detection using only lab-collected data.

This paper is organized as follows. The second section reviews literature relevant to environmental monitoring in the context of IoT, ADCs and ML applications to sensor data telemetry, and Section three presents the architecture of the system being developed. Section four will discuss how the hardware was implemented using CD4051 technology, and Section five describes the software environment used in conjunction with this system, Section six discusses results obtained by measuring laboratory data, and Section seven concludes with a summary of findings and potential future research directions.

\subsection{IoT environmental monitoring and low-cost nodes}
The use of low-cost microcontrollers for environmental sensing has been widely reported. Kumar and Sharma \cite{sensorcloud2019} integrated such nodes with MQTT and cloud platforms for air quality monitoring, demonstrating the viability of cost-effective sensor-to-cloud pipelines. Gupta and Das \cite{iotclimate2021} developed a NodeMCU-based climate control system with Firebase for real-time data exchange, though their work noted limitations in offline storage and local buffering. ESP8266-based deployments have received particular attention owing to built-in Wi-Fi and a large developer ecosystem. Rao and Mehta \cite{esp8266data2022} used the ESP8266 for environmental data acquisition and analytics, while Singh and Reddy \cite{iotgas2023} focused on gas detection and alerting with MQ-series sensors on the same platform; both studies highlighted challenges such as calibration drift and the limited number of analog inputs on the device. Beyond single-node designs, wireless sensor networks have been proposed for larger-scale monitoring: Wang et al. \cite{zigbeewsn2018} employed Zigbee for environmental monitoring, and Ali et al. \cite{lorawan2020} presented a LoRaWAN-based scalable system, trading higher coverage and power efficiency for increased protocol and infrastructure complexity. These works establish a clear trend toward low-cost, connected environmental sensing but often assume either multiple ADC channels or a single sensor type per node, leaving the problem of multi-parameter analog acquisition on a single-ADC device less fully addressed in the literature.

\subsection{ADC expansion and analog multiplexing}
Most microcontrollers have one or two channels of ADC circuitry which limits the number of analog sensors that can connect directly to them without the need of any external device. The CD4051 and CD4052 multiplexers allow an analog signal from multiple sources to be sampled onto one ADC; thus, an interface (mounting board) between an ADC and multiple analog signals is required. For embedded applications such as instrumentation, design requirements are defined for signal ground placement, switching time and settling time for channels selected. Scalable and reconfigurable sensor network systems have previously been described in the literature; particularly prior work on modular sensor fusion and adaptable environmental monitoring services \cite{modularsensors2022} has no specific details on interfacing or timing between the CD4051 and ESP8266; however, in the present situation, the ESP8266 provides only one 10-bit A/D converter (A0); therefore, any multi-channel (analog) design using an ESP8266 must use an external multiplexing device. This document reports the connection interface pin-outs, settling delay, and software sequences that are used when measuring various sensors that use an ESP8266 A/D channel to time multiplex data from those sensors. The concept of sharing one ADC via an analog multiplexer is illustrated in Fig.~\ref{fig:lit-adc-mux}.

\subsection{Laboratory, industrial, and agricultural monitoring}
According to the studies \cite{labmonitoring2020,precisionlab2021}, multiple environmental parameters used for various applications require the use of configurable sampling, storage, and alerting systems. Configurable and modular systems have been reported for environmental monitoring in laboratory settings that take into account multiple different types of physical quantities (i.e., temperature/humidity), with the flexibility of how/when data is logged. Similarly, in manufacturing and industrial settings, studies \cite{reactorsafety2022,processmonitoring2023} demonstrate the requirement for real-time, adaptive systems to help ensure chemical reactor safety and to control the manufacture of chemical/processes, where the monitoring of gas/temperature/pressure is standard \cite{industrialiot2020}. For agricultural and controlled environment growth applications, IoT-based systems have been reported to help with the climate control of the environment and with modular sensor networks that monitor components of the growth process (i.e., soil moisture/light/temp/humidity) which provide additional resources for increasing crop yield \cite{greenhouseiot2019, smartgreenhouse2021}. Therefore, the emphasis of these publications supports a consistent requirement for multi-parameter sensing (i.e., temperature, humidity, gas, light, soil moisture) in laboratory, industrial and agricultural applications and for back-end systems that allow for data storage, visualization, and potential analysis.

\subsection{Cloud backends, storage, and visualization}
When designing a backend for IoT environmental data, there are three important choices: local vs.\ cloud storage, REST vs.\ MQTT/CoAP, and visualization dashboard types. Lightweight relational storage (like SQLite \cite{sqlite2017}) works great for either single node/small-scale or embedded/edge servers, while cloud platforms (like AWS IoT \cite{awsiot2019}) allow for large-scale analytics and multi-tenancy; however, at the cost of operating complexity. RESTful APIs are often preferred for simple push and query scenarios and easily work with web dashboards. Streamlit \cite{streamlit2020} is an example of a rapidly developed data science or IoT dashboard, while modern web frameworks (e.g., React + chart libraries) enable interactive, real-time displays of sensor time series and exported data. The system developed in this paper uses a Flask-based REST API with either SQLite or Supabase (PostgreSQL) for its backend and a React-based dashboard for visualization, resulting in balance among simplicity, portability, and the ability to show multiple parameters and/or machine-learning based predictions within the same interface.

\subsection{ML for sensor data}
Increased use of ML has taken place in environmental and industrial sensor data for purposes such as anomaly detection, forecasting and decision support. \cite{mlanomaly2022} reviewed the literature regarding the use of ML to detect anomalous values within IoT sensor data and demonstrated that many of the ML techniques described can be useful in identifying anomalous values that are not identified using fixed thresholds. LSTMs are frequently used for time series prediction using recurrent architectures when sufficient sequential data exists; research and industry applications have occurred with temperature, humidity and other environmental time series. A limitation of many of the systems in the literature have been that they are trained or evaluated using synthetic or augmented data; the preferred method of training and evaluating a predictive model for deployment in an actual laboratory or facility is by using models that are trained and validated using only collected data since this will provide predictions and/or anomaly flags that more accurately reflect actual operating conditions. Isolation Forest and related algorithms are effective solutions for anomaly detection in cases where few labeled anomalies exist because these algorithms will learn a representation of ``normal'' from the recorded distribution of values \cite{mlanomaly2022}. In the current research study, the researcher trained LSTM models to perform multi-step predictions for each of the five parameters that were recorded and used the Isolation Forest algorithm to detect anomalies and utilized collected data for both the training and evaluation process. \subsection{Positioning of the proposed system}
This system plays an important role in many ways \cite{modularsensors2022,labmonitoring2020}. First, it gives you a physical and repeatable way to connect up your CD4051 to an ESP8266 for doing multi-channel analogue acquisition that includes everything from channel select timing and wiring to making it so each ADC pin can be used for a gas sensor, a light sensor, a soil moisture sensor, and a digital temperature and humidity sensor at the same time. Secondly, it allows you to integrate five different environmental parameters end-to-end (from start to finish) with a Flask backend, storing all of your data in either an SQLite database or a Supabase database \cite{sqlite2017}, and visualising and exporting that data through a React-based dashboard. Lastly, it also implements an ML pipeline (LSTM for predicting future values; Isolation Forests for identifying anomalies) that uses only laboratory data collected during a 5-day deployment period \cite{mlanomaly2022}. There were no synthetic or generated data used when training and evaluating the ML models; therefore, we have strictly adhered to using actual laboratory data only for all aspects described above. These topics/sections will be described in greater detail in later sections.

\section{System overview}
The architecture consists of four main elements: an ESP8266-based sensor node with CD4051 multiplexed analog inputs; a Flask backend with SQLite or Supabase storage; a React web dashboard for visualization; and an ML pipeline that trains on recorded sensor data for prediction and anomaly detection. Fig.~\ref{fig:architecture} illustrates the data flow from the sensors through to the web dashboard and the ML pipeline.

\subsection{Sensor node}
The node is built around the ESP8266MOD. The chip has one ADC input (A0); the CD4051 multiplexer routes one of three analog signals (MQ-6, LDR, soil moisture) to A0 under software control. The node interfaces with:
\begin{itemize}
    \item \textbf{DHT22:} Digital temperature and relative humidity; data pin at GPIO2 (D4) with 10\,k$\Omega$ pull-up. Sampled every 10\,s.
    \item \textbf{MQ-6:} Gas sensor (e.g., LPG); 5\,V supply, analog output connected to CD4051 channel~0. Analog value digitized via A0 after channel selection.
    \item \textbf{LDR:} Light-dependent resistor module; analog output to CD4051 channel~1. Higher ADC value corresponds to higher light level.
    \item \textbf{Soil moisture:} Analog module output to CD4051 channel~2; higher reading indicates wetter soil (module-dependent).
    \item \textbf{CD4051:} 8-channel analog multiplexer; select pins S0, S1, S2 driven by GPIO12 (D6), GPIO13 (D7), GPIO14 (D5); common output Z to ESP8266 A0. Channels 0, 1, 2 used; 3--7 reserved for expansion.
    \item \textbf{JHD162A LCD (I2C):} SDA on GPIO4 (D2), SCL on GPIO5 (D1). Cycles through temperature/humidity, gas, light/soil, and status screens.
    \item \textbf{HW-131:} DC-DC power module; 5\,V output for ESP8266 (VIN), MQ-6, and LCD; 3.3\,V derived where required for DHT22, LDR, soil module, and CD4051.
\end{itemize}
Firmware selects each CD4051 channel in turn, applies a short settling delay (1--2\,ms), then reads A0. All five parameters are sent in one JSON payload via HTTP POST to the backend every 10\,s. On Wi-Fi or sensor failure, status is shown on the LCD and transmission is retried.

\subsection{Backend API}
The backend is implemented in Flask and exposes REST endpoints:
\begin{itemize}
    \item \texttt{/api/sensor-data}: POST from ESP8266; stores timestamped temperature, humidity, gas\_analog, light\_level, soil\_moisture in SQLite or Supabase.
    \item \texttt{/api/latest}: Returns the most recent reading (all five parameters) for the dashboard.
    \item \texttt{/api/stats}: Aggregated statistics (min, max, average) over configurable time ranges for all parameters.
    \item \texttt{/api/health}: Backend and database health.
    \item \texttt{/predict/temperature}, \texttt{/predict/humidity}, \texttt{/predict/gas}, \texttt{/predict/light}, \texttt{/predict/soil}: Prediction endpoints returning LSTM-based forecasts for the requested parameter (e.g., next 1--168\,h).
\end{itemize}
Input validation and error handling are applied; the same schema supports local SQLite and Supabase (PostgreSQL) for deployment flexibility.

\subsection{Data dashboard}
The dashboard is a React (Vite) single-page application with Material-UI and Plotly. It provides:
\begin{itemize}
    \item \textbf{Live and historical charts:} All five parameters visualized with auto-refresh; time-range selection and Plotly zoom/pan.
    \item \textbf{Predictions view:} Single chart showing LSTM predictions for available parameters over a user-selected horizon (e.g., next 24\,h), with values normalized for comparison and original units on hover.
    \item \textbf{CSV export:} Recorded data export for offline analysis.
    \item \textbf{System status:} Last update time, backend health, connectivity indicators.
\end{itemize}
No synthetic or generated data is used; all displayed and exported series are from recorded sensor data and model predictions trained on that data.

\subsection{ML pipeline}

\begin{itemize}
    \item \textbf{Data:} Time-series of temperature, humidity, gas\_analog, light\_level, and soil\_moisture with timestamps are loaded from the database. No synthetic or generated series are added.
    
    \item \textbf{Preprocessing:} Rolling means and change features for all five parameters; optional time-of-day/day-of-week; normalization (e.g., MinMaxScaler). Missing values are filled (e.g., column mean) for robust training.
    
    \item \textbf{Training:} \textbf{LSTM} models per target parameter (five models), trained on sequences of past observations to predict future values (multi-step up to 168\,h); \textbf{Isolation Forest} for anomaly detection on the same recorded feature set.
    \item \textbf{Evaluation:} Hold-out or time-based split on recorded data; metrics such as MAE/RMSE for regression and precision/recall for anomaly detection.
    
    \item \textbf{Deployment:} Trained LSTM and scalers are loaded by the Flask backend; prediction endpoints run cloud-side inference. Anomaly detection can be run on incoming or historical recorded data.
\end{itemize}

All models are trained exclusively on lab-recorded data; the pipeline does not use generated or synthetic datasets.

\section{Hardware implementation}
The hardware is organized around the ESP8266's single ADC (A0). The CD4051 (CMOS 8-channel analog multiplexer/demultiplexer) allows three analog sensors to share A0; the DHT22 uses a digital pin. Key components:

\begin{itemize}
    \item \textbf{ESP8266MOD:} A low-cost, Wi-Fi-enabled system-on-chip microcontroller with an 80\,MHz Xtensa core and built-in 802.11 b/g/n connectivity. In this design it provides the single 10-bit ADC (A0), drives the CD4051 select lines, polls the DHT22, controls the LCD over I2C, and runs the HTTP client. Supply: 3.3\,V logic; VIN from HW-131 5\,V via onboard regulator.
    \item \textbf{DHT22:} A digital temperature and relative-humidity sensor using a capacitive humidity element and a thermistor, with typical accuracies of $\pm$0.5\,°C and $\pm$2\% RH. We connect its data pin to GPIO2 (D4) with a 10\,k$\Omega$ pull-up to 3.3\,V and sample it once per cycle for temperature and humidity.
    \item \textbf{MQ-6:} A semiconductor gas sensor whose conductivity changes in the presence of combustible gases (e.g., LPG, methane). It requires a 5\,V heater supply and outputs an analog voltage proportional to gas concentration. We feed its analog output into CD4051 channel~0; readings are digitized via A0 after selecting that channel (warm-up time required before stable readings).
    \item \textbf{LDR module:} A light-dependent resistor whose resistance decreases with increasing ambient light. The module produces an analog voltage representing light level. We connect its analog output to CD4051 channel~1 and read it via the shared A0 after channel selection.
    \item \textbf{Soil moisture module:} An analog sensor that measures soil moisture by detecting changes in electrical conductivity between two probes. Higher moisture gives higher conductivity and typically a higher output voltage. We connect its analog output to CD4051 channel~2 for digitization through the same A0.
    \item \textbf{CD4051:} A CMOS 8-channel analog multiplexer/demultiplexer IC that routes one of eight analog inputs to a common output under digital control. We use it so that three analog sensors (gas, light, soil) share the ESP8266's single ADC. VDD/VCC to 3.3\,V, VSS/VEE/INH to GND. Address inputs S0 (A)$\to$ GPIO12, S1 (B)$\to$ GPIO13, S2 (C)$\to$ GPIO14; common pin Z$\to$ A0. Y0$\to$ MQ-6, Y1$\to$ LDR, Y2$\to$ soil. A 1--2\,ms settling delay is applied after each channel change before \texttt{analogRead(A0)}.
    \item \textbf{JHD162A LCD (I2C):} A 16$\times$2 character liquid-crystal display with an I2C backpack that reduces wiring to four lines (VCC, GND, SDA, SCL). We use it for local display of temperature, humidity, gas level, light/soil values, and Wi-Fi status. SDA$\to$ GPIO4 (D2), SCL$\to$ GPIO5 (D1).
    \item \textbf{HW-131:} A DC-DC buck (step-down) module that accepts a wide input range (typically 7--28\,V) and provides a regulated 5\,V output. We use it to power the ESP8266 (VIN), MQ-6 heater, and LCD; 3.3\,V is derived where needed for DHT22, LDR, soil module, and CD4051.
\end{itemize}

The LCD cycles through temperature and humidity, gas level with bar, light and soil moisture, and sensor and Wi-Fi status. Firmware samples DHT22 once per cycle, then selects CD4051 channels 0, 1, 2 in sequence with a short delay and reads A0 each time, then sends one JSON payload to the backend every 10\,s. The CD4051 leaves channels 3--7 available for future analog sensors without adding another MCU or ADC.

\section{Software architecture}
The stack has four main parts: embedded firmware, Flask backend, React dashboard, and Python ML pipeline.

\begin{itemize}
    \item \textbf{Embedded Firmware (Arduino C++):} Runs on ESP8266. Initializes DHT22 (GPIO2), CD4051 select pins (GPIO12/13/14), I2C LCD (GPIO4/5), and Wi-Fi. Main loop: read DHT22; for each CD4051 channel 0--2, set S0/S1/S2, delay 1--2\,ms, read A0; format JSON with temperature, humidity, gas\_analog, light\_level, soil\_moisture; update LCD; POST to \texttt{/api/sensor-data}. Retries and LCD messages on failure.
    \item \textbf{Backend (Flask):} Python; SQLite locally or Supabase (PostgreSQL) for production. Routes: sensor-data POST (validate and insert), latest, stats, health, and per-parameter prediction endpoints. Prediction module loads saved LSTM models and MinMax scalers, runs inference, returns time series (e.g., next 1--168\,h). All training data is from recorded sensor readings; no synthetic data is injected.
    \item \textbf{Dashboard (React + Vite + MUI + Plotly):} Single-page app calling backend \texttt{/api/latest}, stats, and prediction APIs. Real-time and historical charts for all five parameters; a combined prediction chart with normalized traces and original units on hover; CSV export of recorded data; health and last-update indicators.
    \item \textbf{ML pipeline (Python):} Preprocessing: load recorded time-series from DB, build rolling and change features for all five parameters, scale (e.g., MinMax). Train one LSTM per target (temperature, humidity, gas\_analog, light\_level, soil\_moisture) and save model + scalers; train Isolation Forest on the same feature set for anomaly detection. Training uses only recorded lab data (e.g., five-day deployment). Inference is invoked by the Flask prediction endpoints.
\end{itemize}

A key algorithm that distinguishes this design is the firmware routine that drives the CD4051 multiplexer so that a single ADC pin on the ESP8266 can sample multiple analog sensors reliably. For each channel, the select pins S0/S1/S2 are set to the channel index, a short settling delay (1--2\,ms) is applied to avoid crosstalk, and then the shared analog input is read (Listing~\ref{lst:cd4051}).
\begin{lstlisting}[
    language=C++,
    basicstyle=\small\ttfamily,
    numbers=left,
    numberstyle=\tiny,
    frame=single,
    caption={CD4051 channel selection and ADC read loop: one ADC serves gas, light, and soil moisture via multiplexer with settle delay.},
    label=lst:cd4051
]
// S0,S1,S2 = GPIO12,13,14; shared analog = A0
const int S0=12, S1=13, S2=14;
int gas_analog, light_level, soil_moisture;
for (int ch = 0; ch < 3; ch++) {
    digitalWrite(S0, ch & 1);
    digitalWrite(S1, (ch>>1) & 1);
    digitalWrite(S2, (ch>>2) & 1);
    delay(2);  // 1-2 ms settling
    int raw = analogRead(A0);
    if (ch == 0) gas_analog = raw;
    else if (ch == 1) light_level = raw;
    else soil_moisture = raw;
}
\end{lstlisting}

End-to-end, data flows from hardware (DHT22 + CD4051 channels) to backend storage, then to the React UI and ML models; all training and evaluation use recorded data only.

\section{Results and discussion}
The system was evaluated using data recorded in a laboratory over five consecutive days. Sensor readings were sampled every 10\,s and transmitted to the backend; the recorded dataset was used for storage, visualization, and ML training. No synthetic or generated data was used. Findings are summarized below.

\begin{itemize}
    \item \textbf{Wi-Fi and upload:} The ESP8266 had good connectivity for the entire duration of testing and all data collected during testing had a consistent time interval of ten seconds. The rate of success of HTTP POST requests was very high and if a POST request failed it was retried. No duplicate timestamps or values were stored.
    \item \textbf{Sensor data:} The sensor data was collected continuously and consisted of five metrics, namely temperature, humidity, gas\_analog, light\_level, and soil\_moisture; DHT22 does give an accurate and stable reading in temperature and humidity; The analog readings for gas, light and soil moisture were accurately produced with consistency through the use of CD4051 channel switching with a 1 to 2\,ms delay, and thus all data collected was used directly for training and evaluation of the system.
    \item \textbf{Backend and interface:} The Flask-based APIs consumed and delivered the collected data, with React being used to present live and historical records of all five parameters and the ability to both predict and export the results. The aggregation and predictions endpoints responded with acceptable latency times to support interactivity.
    \item \textbf{ML using the collected data:} LSTM models were trained against the five target datasets that contained five days of collected data. A statistical isolation forest model was also trained against the same set of features to identify anomalies. Model evaluation was done using some of the collected data that had not been used in the training data set (e.g., based upon time). Anomaly detection successfully identified significant deviations, such as gas or temperature spikes, from the collected data; the LSTM predictions accurately matched the most recent short term trends in the collected dataset. No synthetic or generated data were used in the training or evaluation of either ML model.
    \item \textbf{CD4051 and ADC testing:} No channel-to-channel bleeding or crosstalk was observed while recording the collected analog channels. Sequential S0/S1/S2 signals and settle delays were sufficient to provide reliable multi-channel recording.
\end{itemize}

Fig.~\ref{software_ui} shows the React dashboard with real-time sensor data and analytics derived from the recorded dataset. Predictions and anomaly indicators are produced by models trained exclusively on this recorded lab data. The five-day recorded deployment provided sufficient history for LSTM sequence learning and for Isolation Forest to learn normal baselines and flag anomalies in later recorded segments.

Overall, the EMD delivered stable multi-parameter recording via the CD4051--ESP8266 interface, reliable backend storage and API, and ML-based prediction and anomaly detection trained and evaluated only on recorded sensor data.

\section{Conclusion}
This paper presented an environmental monitoring device (EMD) that uses an ESP8266 and a CD4051 analog multiplexer to acquire five parameters—temperature, humidity, gas (MQ-6), light (LDR), and soil moisture—using a single ADC. A Flask backend (SQLite or Supabase) stores the data and a React dashboard with Plotly provides visualization. An ML pipeline comprising LSTM-based prediction and Isolation Forest for anomaly detection was trained and evaluated solely on five days of recorded lab data; no synthetic data was used. The main contributions are a documented CD4051--ESP8266 interface, end-to-end integration of five environmental variables with local LCD and cloud data storage, a React/Flask stack with optional Supabase storage, and an ML pipeline validated on real sensor data. The prototype is suitable for lab, greenhouse, or other indoor environments and supports multiple analog sensors read through a single ADC. Reference implementation code is available at \href{https://github.com/Prateeeek}{github.com/Prateeeek}.
